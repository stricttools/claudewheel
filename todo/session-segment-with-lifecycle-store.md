# A `session` segment backed by a per-session lifecycle event store

## Context

claudewheel selects profile, version, model, directory, MCP mode and
permissions, then execs Claude Code. Resuming an existing session is the
weakest part of that flow today:

- `--resume <uuid>` requires the caller to already know the uuid and the
  directory it ran under (`cli.py`, the `--resume` member and
  `_check_resume_session`).
- `--picker` appends a bare `--resume`, which opens Claude Code's own picker
  (`cli.py`, the `--picker` member). Its docstring calls it "claudewheel's own
  session picker screen", which it is not. That picker lists sessions by the
  autogenerated AI title, which does not describe what a session was about.
- After a machine crash, reviving the open sessions meant enumerating
  transcripts by hand, reading each one's last `version` and `model`, and
  composing one `claudewheel --profile ... -s version=... --model ...
  --directory ... --resume <uuid>` per session. Every field in that command
  is something claudewheel knew at the original launch and forgot when it
  exec'd.

The idea: make the session a first-class selector, and give it real data to
show.

## Problem

Two things are missing, and they depend on each other:

1. **A place to select a session in the TUI.** There is no segment for it.
   The segments today are profile, github, version, model, directory, mcp,
   permissions (`~/.claudewheel/segments.json`).
2. **Something better than the AI title to show per session.** Claude Code's
   transcript has the prompts but no subject, no phases, and no record of how
   the session ended (clean exit, crash, killed, moved to the background and
   continued under another uuid). Nothing on disk says "this session was
   about X, went through phases A then B, and died in the power loss".

## Design decided so far

### The event store: JSONL, one append-only file per session

Format decision, with the reasoning recorded so it is not re-litigated:

- **JSONL** over TOML, JSON, CSV and SQLite. The data is append-only events
  from many concurrent writers (one hook per running session). A single
  `write()` of one line with `O_APPEND` is atomic on a local filesystem, a
  crash damages at most the last line, and the rest still parses with any
  standard reader. TOML `[[event]]` appends are equivalent on append and
  concurrency but a damaged file fails whole under a strict parser. SQLite
  wins on querying, which nothing here needs, and loses greppability and
  diffs. CSV cannot hold nested or multi-line values.
- **One `<session-uuid>.jsonl` per session**, so no two sessions ever append
  to the same file and deleting a session is deleting a file.
- **Nothing duplicated from the transcript.** Prompts, assistant text, tool
  calls, titles, token counts stay in Claude Code's transcript, which is the
  authority. Events reference transcript messages by the `uuid` each
  transcript line already carries, never by timestamp, so references hold
  across resume, fork and compaction.
- **Shape validated per line by a strictspec-generated validator**, selected
  by `kind`. A bad `format_version` or a failed validation is a hard error
  naming the file and line, never a skipped line. Only a truncated final line
  is tolerated.

Fields every line carries:

| Field | Type | Purpose |
| --- | --- | --- |
| `format_version` | int, starts at 1 | per-line shape marker |
| `id` | ULID | lets a later line supersede or retract this one |
| `at` | RFC 3339 UTC, milliseconds | ordering across writers |
| `session` | session uuid | a line stands alone when grepped or concatenated |
| `source` | `hook`, `generator`, `user`, `import` | who asserted the fact; the UI renders user-written and generated subjects differently; `import` marks backfill |
| `kind` | see below | selects the remaining fields |

Kinds:

| Kind | Fields | Reading rule |
| --- | --- | --- |
| `started` | `cwd`, `profile`, `claude_version`, `model`, `entry` (`new`, `resume`, `continue`, `fork`, `background`), `parent` (uuid or null), `transcript` (path) | one per process start on the session; latest by `at` is the current launch |
| `ended` | `outcome` (`exited`, `crashed`, `killed`, `backgrounded`, `unknown`), `continued_in` (uuid or null), `detail` | latest wins; `backgrounded` links to the fork's uuid |
| `subject` | `text` | one line, latest wins |
| `tags` | `tags` (list of strings) | latest wins, whole list replaced |
| `arc` | `arc_id` (ULID), `label`, `summary`, `start` (message uuid), `end` (message uuid or null while open) | latest per `arc_id` wins; opening, closing and relabeling are all re-emissions |
| `note` | `text`, `anchor` (message uuid or null) | free annotation |
| `retract` | `target` (event id), `reason` | removes the target from every view |

### The segment

- A `session` segment, **optional**, ordered after `directory`, because
  transcripts live under one encoded directory each and
  `_check_resume_session` already refuses a uuid whose directory does not
  match.
- Options: the transcripts under the chosen directory, newest activity first,
  plus "new session" as the default.
- Each row shows subject, tags and outcome from the event store. A session
  with no recorded subject says so explicitly. The AI title is never used as
  a fallback.
- Picking a row prefills profile, version, model and permissions from the
  session's latest `started` event. That is the manual work the crash
  recovery required, done by the launcher.
- Rows whose latest event is `ended` with `outcome: crashed`, or that have a
  `started` with no `ended` at all, are the ones to revive after a crash.

## Open decisions

These need the user, not an implementor.

1. **Boundary.** Either the event store and a web lifecycle view are a
   separate tool and claudewheel gets one segment that reads the same files,
   or the whole thing lives in claudewheel. The first keeps the launcher a
   launcher; the second makes it grow a web server. The user's stated aim is
   a new tool for the visual lifecycle view, which points at the first.
2. **Who writes `ended`.** claudewheel execs into Claude Code
   (`launch.py`, `do_launch`) and cannot observe the exit. Options: a
   session-end hook deployed with the existing hooks under
   `~/.claudewheel/scripts/`; or a launch-time sweep that marks transcripts
   with no clean end as `crashed`; or both, with the sweep as the crash
   path only.
3. **Who writes `subject`, `tags`, `arc`.** A generator that reads
   transcripts, and the user editing them. Whether the generator is a
   claudewheel subcommand or belongs to the separate tool follows from
   decision 1.
4. **Required or optional segment.** Optional is the design above; a
   required segment would force "new session" to be an explicit choice on
   every launch.

## Affected files

- `claudewheel/cli.py`: the `--resume` / `--picker` / `--continue` members
  and `_check_resume_session`; the `--picker` docstring is wrong today and
  should be corrected regardless of this todo.
- `claudewheel/launch.py`: `resolve_launch_config` builds cwd, argv, env; the
  natural place to write the `started` event before `do_launch`.
- `claudewheel/clients.py`: `build_claude_argv` composes `--resume`.
- `~/.claudewheel/segments.json` and `options.json`: a new segment entry with
  its discovery.
- `claudewheel/guardrail.py`: the hook wirings, if a session-end hook is the
  answer to decision 2.
- A new module for reading the event store, validated by a
  strictspec-generated validator.

## Effort

Medium. The segment itself follows the existing segment pattern. The event
store reader and its validator are small. The generator for subjects and
arcs is the largest piece and depends on decision 1, so it may not be this
project's work at all.
